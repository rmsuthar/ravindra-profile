# Capstone Project: Global-Edge Payment Gateway Mock

This document provides a detailed architectural blueprint and implementation guide for building a mock payment gateway. This project is specifically designed to showcase the exact skills required for senior architecture roles at payment processors like Mastercard and Visa.

## Core Architecture Overview

The system consists of three main components:
1. **The Merchant Frontend (React)**: Hosts the checkout form but uses secure iFrames to isolate sensitive data.
2. **The Edge Gateway (Cloudflare Workers + Upstash Redis)**: Handles routing, idempotency, rate-limiting, and AI risk scoring.
3. **The Core Processor (Mock Backend API)**: A serverless function that accepts the tokenized payment and simulates authorization.

---

## 1. Secure UI: Isolated iFrames Architecture

**The Problem:** If a merchant's website is compromised via Cross-Site Scripting (XSS), attackers can read any data typed into standard `<input>` fields, including Credit Card PANs (Primary Account Numbers). This violates PCI-DSS requirements.
**The Solution:** The PAN and CVV inputs must be hosted in an `iframe` served from a different domain (your secure payment domain). The parent DOM cannot access the iframe's contents due to the Same-Origin Policy.

### Implementation Steps:
1. **Create the Secure Application:**
   - Build a highly optimized app served from `secure.yourdomain.com`. There are two architectural approaches:
   - **Standard Approach (React/HTML):** Uses standard `<input>` elements. This is the industry standard (Stripe, Braintree). Vulnerable to DOM-scraping keyloggers *if* not properly isolated in the iframe.
   - **Advanced Approach (Raw CanvasKit/WebGL or PixiJS):** Render the input fields purely as pixels on a `<canvas>` without a heavy framework like Flutter. Because there are no semantic DOM elements, standard DOM-scraping XSS malware cannot read the credit card numbers on the screen.
   - **Architectural Trade-offs of Canvas Rendering:** 
     - *Pros:* Defeats DOM scraping; microscopic bundle size (if using raw Canvas API or PixiJS).
     - *Cons:* You must manually build the blinking cursor, text selection, and accessibility (ARIA overlays). Crucially, to trigger mobile keyboards (iOS/Android), you are forced to overlay a hidden transparent `<input>` anyway, which attackers could target.
   - **The Golden Rule:** Regardless of whether you use React or Canvas, you **must still use the cross-origin iframe**. If the canvas is embedded directly in the merchant DOM, a global `window.addEventListener('keydown')` keylogger can still capture keystrokes. The iframe boundary is what defeats global keylogging.
2. **Create the Merchant App:**
   - Build a standard checkout page (e.g., Next.js) served from `merchant.com`.
   - Embed the `secure.yourdomain.com` iframe where the card inputs should go.
3. **Cross-Origin Communication:**
   - Use the `window.postMessage` API for communication.
   - When the user clicks "Pay" on the merchant site, the merchant app sends a `postMessage({ action: 'SUBMIT' })` to the iframe.
   - The iframe submits the raw card data to the Edge Gateway.
   - The Edge Gateway returns a single-use "Token" to the iframe.
   - The iframe sends the Token back to the parent merchant app via `postMessage({ token: 'tok_123abc' })`.
   - The merchant app submits the final checkout payload (items, amount, and the secure Token) to its own backend.

## 2. Edge Idempotency & Rate Limiting

**The Problem:** Network connections drop. If a user clicks "Pay", the request reaches the server, the card is charged, but the connection drops before the success response reaches the user. The user clicks "Pay" again. They are charged twice.
**The Solution:** Idempotency keys. Every payment request must include a unique UUID generated by the client.

### Implementation Steps:
1. **Setup Upstash Redis:**
   - Use Upstash because it provides REST-based Redis access that works perfectly inside Cloudflare Workers.
2. **Client-Side Generation:**
   - When the checkout page loads, generate a UUID `Idempotency-Key` (e.g., `req_987xyz`).
3. **Cloudflare Worker Logic (The Interceptor):**
   - When the payment request hits the Worker, extract the `Idempotency-Key` header.
   - Check Redis: `GET idempotency:req_987xyz`.
   - **If it exists:** The request is a duplicate. Immediately return the cached successful (or failed) response from Redis without processing the payment again.
   - **If it does not exist:**
     - Proceed to process the payment (or forward it to the Core Processor).
     - Once the Core Processor responds, store the response in Redis: `SET idempotency:req_987xyz <response_payload> EX 86400` (expires in 24 hours).
4. **Rate Limiting:**
   - Before checking idempotency, implement a sliding window rate limiter in Redis to ensure a single IP or merchant API key cannot spam payment requests (e.g., max 10 requests per second).

## 3. AI Fraud Engine: Behavioral Telemetry

**The Problem:** Traditional fraud detection relies only on static data (IP address, billing zip code). Modern fraud rings use stolen data that looks legitimate.
**The Solution:** Behavioral Biometrics. Analyze *how* the user inputs the data, not just *what* they input. Bots fill forms instantly; legitimate users hesitate, use backspace, and type at specific cadences.

### Implementation Steps:
1. **Telemetry Collection (Frontend):**
   - Inside your secure iFrame, add event listeners for `keydown`, `keyup`, `paste`, and `mousemove`.
   - Calculate metrics:
     - `timeToComplete`: Total time from first keystroke to form submission.
     - `backspaceCount`: Number of corrections made.
     - `pasteEvent`: Did they type the 16-digit card or paste it? (Pasting is higher risk unless combined with a password manager signature).
     - `keystrokeCadence`: Average time between keystrokes.
2. **Edge AI Processing (Cloudflare Workers AI):**
   - When the iFrame submits the raw card data to the Edge Gateway, it includes this telemetry payload.
   - In your Cloudflare Worker, utilize **Workers AI** (e.g., using a lightweight classification model or even a structured prompt to Llama 3 for risk scoring).
   - **Example AI Prompt/Input:**
     ```json
     {
       "telemetry": {
         "timeToComplete_ms": 120, 
         "pasted": true,
         "ip_country": "US",
         "billing_country": "GB"
       }
     }
     ```
   - If the AI returns a `RiskScore > 85`, the Edge Gateway immediately blocks the transaction (returns `403 Fraud Suspected`) before it ever reaches the Core Processor.

## Summary of the Request Flow

1. User types in card details (Inside Secure iFrame).
2. Frontend collects telemetry (typing speed, paste events).
3. User clicks "Pay". Frontend generates `Idempotency-Key` and sends it with telemetry and card data to Cloudflare Worker.
4. **Worker Step 1:** Rate Limit Check.
5. **Worker Step 2:** Idempotency Check (Redis).
6. **Worker Step 3:** AI Risk Score Evaluation (Workers AI).
7. **Worker Step 4:** Forward to Mock Core Processor for simulated settlement.
8. **Worker Step 5:** Cache response in Redis against the Idempotency Key.
9. Return Success/Fail to the UI.
